# CraftPlanner 設計書

ゲーム素材・レシピ管理アプリ（企画書兼実装指示書）に基づく設計書。
実装はこの文書の方針に従う。仕様が変わった場合はこの文書も更新する。

---

## 1. 技術構成と選定理由

| 項目 | 採用 | バージョン |
| --- | --- | --- |
| 言語 | C# 13 | .NET 10 SDK（LTS） |
| UI フレームワーク | WPF（Windows Presentation Foundation） | .NET 10 同梱 |
| MVVM 補助 | CommunityToolkit.Mvvm | 8.4.0（MIT） |
| JSON | System.Text.Json | .NET 10 同梱 |
| テスト | xUnit | 2.9.3 |
| 開発環境 | Visual Studio 2026 Community（確認済み）または `dotnet` CLI | - |

### 選定理由

* **オフライン動作・ファイル操作の厳密な制御**: .NET の `System.IO` で保存先をアプリ専用フォルダーに限定でき、外部通信は一切不要。Web 技術系（Electron / Tauri）と比べ、ブラウザのサンドボックスや IPC を介さず、ファイル操作の責務を 1 つのサービスに集約しやすい。
* **ノードキャンバスの実装容易性**: WPF の `Canvas` と `RenderTransform`（拡大縮小・平行移動）でズーム・パン・ノード移動・ベジェ曲線の接続線を標準機能だけで実装できる。追加ライブラリ不要。
* **単体テスト**: 計算・保存・入出力は UI 非依存の `CraftPlanner.Core`（通常のクラスライブラリ）に置き、xUnit でテストする。WPF 側はビューモデルを介して Core を呼ぶだけにする。
* **デバッグ手段**: Visual Studio のデバッガー、ライブビジュアルツリー、XAML ホットリロードが使える。開発者の既存環境と一致する。
* **依存の少なさ**: 追加 NuGet は MVVM ボイラープレート削減のための CommunityToolkit.Mvvm のみ。これは Microsoft が保守している。
* **将来性**: WPF は .NET 10 で引き続きサポート。データ形式は JSON にバージョン番号を持たせ、Core 内の移行処理で将来の変更に対応する。

### 不採用の候補

* **WinUI 3**: ツールチェーンが WPF より不安定で、ズーム可能キャンバスの実装例も少ない。
* **Avalonia**: クロスプラットフォームだが Windows 専用の本件では追加依存が増えるだけ。
* **Tauri / Electron（Web 技術）**: フロントエンドとバックエンドの 2 言語になり保守負担が増える。ファイル操作が IPC 越しになり、安全性の確認箇所が分散する。

### 必要な開発環境

1. Visual Studio 2026 Community（「.NET デスクトップ開発」ワークロード）。確認済み。
2. .NET 10 SDK。確認済み（10.0.401）。
3. ビルド: `dotnet build`、テスト: `dotnet test`（どちらも `CraftPlanner.slnx` のあるフォルダーで実行）、実行: `dotnet run --project src/CraftPlanner.App`。

## 3. データモデル

### 3.1 ID

* すべて文字列。`IdGenerator` が `item-xxxxxxxx` のような接頭辞＋8 桁の英数字を発行し、既存 ID との衝突を確認する。
* アイテム ID はユーザーが CSV で `iron_ingot` のような読みやすい ID を付けることもできる（空欄なら発行）。
* 参照はすべて ID で行う。名前は識別に使わない。

### 3.2 ゲームデータ（1 ファイル）

```
GameData
  formatVersion : int        保存形式バージョン（現在 1）
  id, name                   ゲームデータ ID と表示名
  items : Item[]
    id, name, summary, description, acquisition
    iconPng : string?        PNG を Base64 で埋め込み（最大 128x128 に縮小）
    recipes : Recipe[]       このアイテムを出力するレシピ
      id, name, outputQuantity (>=1)
      materials : { itemId, quantity (>=1) }[]   同じ itemId は 1 行まで
```

「このアイテムを使うレシピ」は保存せず、`GameData.FindUsages(itemId)` で導出する。

### 3.3 制作計画（1 ファイル）

```
Plan
  formatVersion, id, name, gameDataId
  displayMode : Simple | Detailed       計画全体で切替（提案、10 章参照）
  inventory : { itemId: quantity }      計画内の所持数
  nodes : PlanNode[]
    ItemNode: id, itemId, x, y, requiredQuantity(目標時のみ使用), selectedRecipeId,
              isExpanded, isCollapsed, isCycleTerminal
    MemoNode: id, x, y, width, height, text, colorKey
  edges : { id, parentNodeId, childNodeId, materialItemId }[]   有効な接続
  severedEdges : { parentNodeId, materialItemId }[]             切断された接続
  view : { offsetX, offsetY, zoom }
```

* 親を持たない ItemNode が「目標」。`requiredQuantity` はその目標の必要数量。
* 子ノードの必要数量は計算で導出し、保存しない（親の制作回数×素材数）。
* 同じ itemId のノードが複数あっても統合しない。各ノードは最大 1 本の親接続を持つ（森構造）。

### 3.4 アプリ設定（settings.json）

開いているタブの計画 ID、アクティブタブ、ウィンドウサイズ、バックアップ世代数、最後に選んだゲームデータ。

## 4. 保存・バックアップ

### 4.1 保存先（アプリ専用領域のみ）

```
%LOCALAPPDATA%\CraftPlanner\
  games\{gameId}.json
  plans\{planId}.json
  settings.json
  backups\games\{gameId}\{yyyyMMdd-HHmmss-fff}.json
  backups\plans\{planId}\...
  backups\settings\...
  logs\app-yyyyMMdd.log
```

`AppPaths` がすべてのパスを決定し、`SafeFileStore` 以外はファイルを書かない。
この領域の外に触れるのは、ユーザーがファイルダイアログで明示的に選んだ画像／JSON／CSV の **読み込み** と、エクスポート先への **新規書き込み** だけ。インポート元ファイルは変更しない。

### 4.2 書き込み手順（SafeFileStore）

1. `{file}.tmp` に書き込み、フラッシュする。
2. `.tmp` を読み戻してパースし、検証に通った場合のみ次へ。
3. 既存ファイルがあれば `backups\` にタイムスタンプ付きで複製する。
4. `File.Move(tmp, file, overwrite: true)` で置き換える。
5. 世代数（既定 10）を超えた古いバックアップを削除する。削除対象は `backups\` 配下の自アプリ命名規則のファイルだけ。

失敗した場合は例外をそのまま UI に伝え、「未保存の変更あり」を表示する。成功表示はしない。

### 4.3 読み込み

* 起動時に `games\`・`plans\` の全 JSON を読み、`formatVersion`・必須項目・参照整合性を検証する。
* 読み込みに失敗したファイルは **そのまま残し**、エラー一覧（ファイル名・原因・復旧手段）を表示する。初期データで上書きしない。
* バックアップ一覧から復元できる。復元時も現在のファイルを先にバックアップする。

### 4.4 自動保存

編集後 1.5 秒のデバウンスで保存。Ctrl+S は即時保存。タブを閉じる・終了時にも保存。保存状態（保存済み／未保存／失敗）をステータスバーに常時表示する。

## 5. 素材計算（PlanCalculator）

入力: `Plan`、`GameData`。出力: `CalculationResult`（ノード別・アイテム別・目標別・警告）。
UI、ノード位置、登録順に依存しない純粋関数。

### 5.1 用語

* **目標ノード**: 親接続のない ItemNode。需要 = `requiredQuantity`。
* **制作ノード**: `isExpanded` かつ有効な `selectedRecipeId` を持つノード。レシピを適用し制作回数を計算する。
* **末端ノード**: 制作ノードでないノード。需要は「そのアイテム自体を用意する」必要数となる。
* **切断**: 切断された素材の需要は計算しない（下流停止）。折りたたみは計算に影響しない。

### 5.2 手順（計画全体の確定値）

1. 有効接続から **アイテム間グラフ**（親アイテム → 素材アイテム）を作り、強連結成分（SCC）を求める。サイズ 2 以上または自己ループの SCC を「循環」とする。
2. SCC の位相順（製品側から素材側へ）にアイテムを処理する。
3. アイテム I について
   * 総需要 Gross(I) = そのアイテムの全ノードの需要の合計（目標は requiredQuantity、子は親の制作回数×素材数）。
   * 所持数は計画全体で 1 回だけ差し引く: Net(I) = max(0, Gross − 所持数)。
   * Net を各ノードに需要比で按分（最大剰余法。端数の順序は 末端優先 → レシピ ID → ノード ID で固定）。
   * 同じレシピの制作ノードは **まとめて** 制作回数 = ceil(按分需要合計 / 完成数) を求め、余剰 = 制作数 − 需要。余剰はまず同アイテムの末端ノードの不足に充当し、残りを「余剰」として表示する。
   * 制作回数をノードへ需要比で配分し、各ノードの有効接続に沿って子ノードの需要（回数×素材数）を確定する。
   * 末端ノードの不足数 = 按分需要 − 充当分。アイテムの不足数 = 末端の不足合計。
4. 循環 SCC に属するアイテムは、森の深さ順にノード単位で ceil 計算し、所持数は末端合計に 1 回だけ適用する。結果は `isUncertain = true` で返し、その下流アイテムも不確定とする。計画全体の計算は止めない。

これにより企画書 7.3 の例（剣 3 個 + 独立目標 5 個、所持 2 → 不足 6）と、7.2 の複数個完成・余剰再利用を満たす。

### 5.3 目標別の参考値

目標ごとに、その目標の部分木だけを入力として所持数 0 で同じ計算を行い、アイテム別の必要数を出す。表示では所持数（計画共通）と参考不足数 = max(0, 必要数 − 所持数) を添え、「参考値」と明示する。確定値は 5.2 の計画全体のみ。

### 5.4 制作可能の判定

ノードの各素材について「必要数 ≤ 所持数」なら直接制作可能、子が再帰的に制作可能なら間接制作可能。切断された素材は所持数だけで判定する。表示の強調に使い、数量計算には影響しない。

### 5.5 循環レシピの展開

ツリー展開時、祖先に同じアイテムが現れたノードを `isCycleTerminal` とし、その素材を 1 世代分だけ末端ノードとして生成して再帰を止める。警告色で表示する。

## 6. ツリー操作（Planning）

* **展開**: 選択レシピの素材ごとに子ノードを生成し、再帰的に展開する（素材 0 種類なら子なし）。
* **折りたたみ**: `isCollapsed` のみ変更。子孫を非表示にする。計算・位置は保持。
* **切断**: 接続を `severedEdges` に移し、子以下の部分木を削除する。切断マーカーをクリックすると再接続し、部分木を再生成・自動配置する。
* **レシピ変更**: プレビュー（計算せず素材一覧のみ表示）→ 確定で子を再生成。新旧で共通の素材の子ノードは位置を保持する。
* **自動配置**: 親の右側 (x = 親右端 + 40) から縦方向に ±40 段、見つからなければ右へ 1 列ずらして最大 20 列探索。見つからない場合は最初の候補位置に置き、重なりを通知する（既存ノードは動かさない）。
* **コピー／貼り付け／複製**: 選択ノード群と、その中で閉じている接続をコピー。貼り付けは +30,+30 にずらして新 ID で生成。

## 7. Undo / Redo（History）

計画ごとに `HistoryManager` を持ち、編集 1 回ごとに計画全体のスナップショット（JSON 深いコピー）を保存するメメント方式。
コマンド方式より実装が単純で「Undo がデータを壊さない」ことを確認しやすい。
ノードのドラッグはマウスを離した時点、メモ文字入力はフォーカス喪失時に 1 件として記録する。
ズーム・パン・全体表示は履歴に含めない。履歴上限 200 件。

---

## 8. JSON / CSV

* **ゲームデータ JSON**: 保存形式そのもの。アイコン込み。インポートは「新規作成」または「既存へ統合」。統合時は ID 競合ごとに「更新（差分表示）／新 ID で別アイテム／除外」を選ぶ。
* **制作計画 JSON**: `gameDataId` が一致しない場合は拒否し、元のゲームデータを案内する。
* **CSV（アイテム）**: 列 `id,name,summary,description,acquisition`。UTF-8（BOM 付き）、Excel 互換。空 ID 行は行ごとに「新 ID で取り込む／取り込まない」、競合行は「更新／新 ID／除外」を選ぶ。CSV 内で同じ ID が重複している場合は取り込みを中止し、該当行を表示する（提案）。
* **CSV（レシピ）**: 列構成を 10 章で提案中。確認が取れるまでエクスポートのみ提供し、インポートは未実装とする。
* インポートは全件検証 → 確認 → 一括適用。適用前に対象ファイルをバックアップする。

## 10. 未確定事項への提案

| 項目 | 提案 | 影響 |
| --- | --- | --- |
| レシピ CSV の列構成 | 1 素材 1 行: `recipe_id,output_item_id,recipe_name,output_quantity,material_item_id,material_quantity`。素材 0 種類は素材列を空にした 1 行。更新ルール: `recipe_id` 一致なら素材一覧を CSV 側で全置換、空なら新規発行。 | **確認が必要**。確認後にインポートを実装 |
| CSV 内の ID 重複 | 取り込みを中止し重複行を表示 | 小。安全側なので実装済み（変更可） |
| 表示モードの切替単位 | 計画全体で切替（企画書 3.4 の保存項目が単数のため） | 小。ノード単位にする場合はモデルに 1 項目追加 |
| 同一アイテムで異なるレシピ選択時の余剰 | 所持数・需要は需要比で按分し、制作余剰は同アイテムの末端ノード不足に充当。残りは余剰表示 | 中。5.2 に記載の方式で実装 |
| 自動配置の再探索上限 | 縦 ±40 段 × 横 20 列。超えたら重ねて配置し通知 | 小 |
| バックアップ世代数・保存先 | 既定 10 世代、`%LOCALAPPDATA%\CraftPlanner\backups`。settings.json で世代数変更可 | 小 |
| アイコンの保存サイズ | 読み込み時に最大 128×128 PNG に縮小して埋め込む（JSON 肥大化防止） | 小 |
